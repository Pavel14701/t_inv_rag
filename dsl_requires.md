Требования к расширению DSL (Roadmap)
1. Поддержка переменных и присваиваний
Текущее состояние:
Выражение вычисляется за один проход, невозможно сохранить промежуточный результат или переиспользовать значение.

Требование:
Добавить конструкцию let, позволяющую объявить локальную переменную внутри выражения.

Синтаксис (пример):

text
let oversold = rsi.value < 30
let price_above_ott = close > ott.ott
oversold and price_above_ott
Семантика:

Переменные существуют только в области видимости текущего правила.

Не могут ссылаться на будущие значения (только на уже вычисленные индикаторы и ранее определённые переменные).

Реализация на уровне AST: узел Let(var_name, value_expr, body_expr). Интерпретатор сохраняет значение в локальном словаре и подставляет его при обращении.

Безопасность:
Переменные не имеют доступа к внешнему состоянию, только к значениям, возвращённым контекстом. Присваивание – это простая подстановка числа/булева значения.

2. Временные зависимости и функции over-time
Текущее состояние:
Нельзя описать паттерны, зависящие от нескольких последовательных баров («RSI растёт три бара подряд»). Требуется предварительно создавать специальные индикаторы (например, rsi_increasing(3)).

Требование:
Добавить в DSL оператор over, позволяющий ссылаться на предыдущие значения индикаторов или выражений.

Синтаксис (примеры):

text
rsi.value > rsi.value[1] over 3 bars
или с ключевым словом:

text

x[offset] – значение x на offset баров назад. Реализуется в интерпретаторе через запрос к контексту, который хранит историю индикаторов.

rising(expr, n) – истина, если expr строго возрастает на протяжении n последних баров (включая текущий).

Расширить грамматику поддержкой постфиксного оператора [N] или функций rising/falling.

Техническое задание на разработку DSL (Domain‑Specific Language) для торговых стратегий
1. Общие сведения
1.1. Наименование системы
DSL (Domain‑Specific Language) для описания торговых сигналов.

1.2. Назначение
DSL предназначен для декларативного описания условий входа и выхода из сделок на основе значений индикаторов, без написания исполняемого кода. Является частью автоматизированной торговой системы, формируя первичный сигнал (булево значение), который затем обрабатывается ML‑моделью и риск‑менеджментом.

1.3. Область применения
Определение пользовательских торговых стратегий через текстовые правила.

Бэктестинг на исторических данных.

Интеграция в REST/WebSocket API торгового ядра.

2. Функциональные требования
2.1. Язык выражений
DSL должен поддерживать:

Литералы: целые и вещественные числа (например, 30, 1.5).

Идентификаторы: имена индикаторов и их атрибутов, доступ через точечную нотацию (например, rsi.value, ott.ott, close).

Операторы сравнения: <, >, <=, >=, ==, !=.

Логические операторы: and, or, not.

Скобки для группировки: ( и ).

2.2. Грамматика (формальная)
Формальная грамматика в нотации, близкой к EBNF:

ebnf
expression   = or_expr ;
or_expr      = and_expr { "or" and_expr } ;
and_expr     = not_expr { "and" not_expr } ;
not_expr     = "not" not_expr | comparison ;
comparison   = atom [ comp_op atom ] ;
comp_op      = "<" | ">" | "<=" | ">=" | "==" | "!=" ;
atom         = NUMBER | indicator_access | "(" expression ")" ;
indicator_access = IDENTIFIER { "." IDENTIFIER } ;
Примечания:

Ключевые слова (and, or, not) регистрозависимы, только строчные буквы.

Идентификаторы (IDENTIFIER) и числа (NUMBER) соответствуют регулярным выражениям [a-zA-Z_][a-zA-Z0-9_]* и \d+(\.\d+)?.

Пробелы между токенами игнорируются.

2.3. AST (абстрактное синтаксическое дерево)
DSL-парсер должен преобразовывать входную строку в AST, состоящее из следующих узлов:

Number(value: float) – числовой литерал.

IndicatorAccess(indicator_name: str, attrs: list[str]) – доступ к значению индикатора.

Comparison(op: str, left: ASTNode, right: ASTNode) – операция сравнения.

BinOp(op: str, left: ASTNode, right: ASTNode) – бинарная логическая операция (and, or).

NotOp(expr: ASTNode) – логическое отрицание.

AST не должен содержать ссылок на синтаксические конструкции исходного текста и быть полностью независимым от грамматики.

2.4. Интерпретатор
Интерпретатор должен рекурсивно обходить AST и вычислять итоговый булев результат на основе переданного контекста.

Контекст – объект, предоставляющий метод:

text
get_indicator(name: str, attrs: list[str]) -> float
Контекст отвечает за получение текущих значений индикаторов из ядра системы.

Логика вычисления:

Number – возвращает своё значение.

IndicatorAccess – вызывает context.get_indicator(name, attrs).

Comparison – вычисляет левый и правый операнды, применяет оператор сравнения.

BinOp – вычисляет левый и правый операнды, применяет and/or.

NotOp – вычисляет операнд и возвращает логическое отрицание.

2.5. Безопасность
DSL не должен поддерживать исполняемый код. Запрещается использование eval(), exec() или генерация Python-кода из выражений DSL.

Интерпретатор может вызывать только метод get_indicator контекста. Никакие другие объекты, файловая система или сеть не должны быть доступны.

Контекст должен проверять, что запрашиваемое имя индикатора входит в белый список разрешённых, иначе генерировать исключение.

2.6. Обработка ошибок
При синтаксических ошибках парсер должен возвращать понятное сообщение с указанием позиции ошибки.

При семантических ошибках (неизвестный индикатор, неверный тип в сравнении) интерпретатор должен выбрасывать исключения с информативным описанием.

3. Нефункциональные требования
3.1. Производительность
Парсинг типового выражения (< 50 символов) не должен превышать 1 мс на стандартном оборудовании.

Интерпретация AST не должна создавать значительной вычислительной нагрузки (не более 0.1 мс).

3.2. Расширяемость
Грамматика должна быть реализована в отдельном модуле, допускающем добавление новых операторов и узлов AST.

Интерпретатор должен быть спроектирован так, чтобы легко добавлять новые типы узлов через наследование или паттерн Visitor.

3.3. Надёжность
Компоненты DSL должны быть покрыты юнит-тестами: для парсера – проверка корректных и некорректных входных строк, для AST и интерпретатора – проверка правильности вычислений на различных контекстах.

3.4. Переносимость
Код должен быть написан на Python 3.10+ без привязки к операционной системе.

4. Требования к реализации
4.1. Инструменты
Парсер: библиотека lark (LALR-парсер). Допускается использование других парсеров при сохранении совместимости.

Интерпретатор: чистый Python, без внешних зависимостей, кроме стандартной библиотеки.

4.2. Структура модуля
Проект должен содержать:

dsl/grammar.lark – файл грамматики.

dsl/parser.py – загрузка грамматики и функция parse(code: str) -> ASTNode.

dsl/ast.py – определения классов узлов AST.

dsl/interpreter.py – класс Interpreter с методом visit(node, context) -> bool.

dsl/context.py – интерфейс контекста (абстрактный класс или протокол).

4.3. API для интеграции
Предоставить функцию:

python
def evaluate_dsl(code: str, context: Context) -> bool:
    ast = parse(code)
    interpreter = Interpreter()
    return interpreter.visit(ast, context)
которая будет использоваться в обработчиках HTTP‑запросов.

5. Перспективные требования (вторая очередь)
На основе анализа ограничений первой версии планируется расширение DSL:

5.1. Переменные
Ввести конструкцию let <name> = <expression> in <body>, позволяющую сохранять промежуточные результаты и переиспользовать их без повторного вычисления.

5.2. Временные зависимости
Реализовать доступ к историческим значениям индикаторов через синтаксис indicator[offset], где offset – количество баров назад.
Добавить встроенные функции rising(expr, n) и falling(expr, n), возвращающие истину, если выражение монотонно возрастает/убывает n последних баров.

5.3. Пользовательские функции (макросы)
Разрешить определять именованные блоки правил с параметрами, которые затем могут быть вызваны в основном выражении. Макросы должны раскрываться на этапе парсинга в AST, не вводя динамического исполнения.

6. Этапы разработки и приёмка
Этап 1. Базовая версия
Реализация грамматики, парсера, AST, интерпретатора.

Тестирование на наборе из ≥20 примеров (включая ошибочные).

Интеграция в API ядра (эндпоинт /evaluate).

Критерии приёмки:

Все примеры из спецификации вычисляются корректно.

Попытка использовать неразрешённые операции (вызов функций, присваивание) приводит к ошибке парсинга.

Время обработки запроса ≤ 2 мс.

Добавление let-переменных.

Поддержка временных зависимостей ([offset], rising/falling).

Обновление документации и тестов.

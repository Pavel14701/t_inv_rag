# Техническое задание на разработку DSL для описания торговых сигналов

**Версия 2.0** (с поддержкой протокола индикаторов)  
**Дата:** 2026-07-19

---

## 1. Общие сведения

### 1.1. Наименование системы
DSL (Domain‑Specific Language) для декларативного описания условий входа/выхода из сделок.

### 1.2. Назначение
DSL предназначен для задания логики торговых сигналов на основе значений индикаторов без написания исполняемого кода. Сигнал (булево значение) используется автоматизированной торговой системой, ML-моделью и риск-менеджментом.

### 1.3. Область применения
- Определение стратегий в текстовом виде.
- Бэктестинг на исторических данных.
- Интеграция через REST/WebSocket API.
- Кросс-языковая поддержка: реализации на Python, JavaScript, C++, Go и др. с единым протоколом.

### 1.4. Принцип работы
Пользователь вводит строку-выражение. Парсер строит абстрактное синтаксическое дерево (AST). Интерпретатор вычисляет AST, используя контекст, который получает значения индикаторов через **протокол провайдеров**. Результат – `true`/`false`.

## 2. Функциональные требования

### 2.1. Базовый синтаксис
DSL поддерживает:
- **Числовые литералы** (целые и вещественные): `30`, `1.5`, `0.0`.
- **Идентификаторы индикаторов** в точечной нотации: `rsi.value`, `ott.ott`, `close` (имя индикатора и атрибут, разделённые точкой).
- **Операторы сравнения**: `<`, `>`, `<=`, `>=`, `==`, `!=`.
- **Логические операторы** (строчные, регистрозависимые): `and`, `or`, `not`.
- **Скобки** для группировки: `(` и `)`.

Пример: `(rsi.value < 30) and (close > ott.ott)`

### 2.2. Формальная грамматика (EBNF)
Грамматика, единая для всех реализаций:

```
expression   = or_expr
or_expr      = and_expr { "or" and_expr }
and_expr     = not_expr { "and" not_expr }
not_expr     = "not" not_expr | comparison
comparison   = atom [ comp_op atom ]
comp_op      = "<" | ">" | "<=" | ">=" | "==" | "!="
atom         = NUMBER | indicator_access | "(" expression ")"
indicator_access = IDENTIFIER { "." IDENTIFIER }
```

- **IDENTIFIER**: `[a-zA-Z_][a-zA-Z0-9_]*`
- **NUMBER**: `\d+(\.\d+)?`
- Пробелы и табуляции игнорируются. Комментарии не предусмотрены.

### 2.3. AST (абстрактное синтаксическое дерево)
AST должно быть **языково-независимым**, сериализуемым в **JSON** для передачи между компонентами.

Типы узлов:
- `Number` – поле `value` (float).
- `IndicatorAccess` – поля `indicator` (строка) и `attributes` (список строк, например `["rsi", "value"]`).
- `Comparison` – поля `operator` (`"<"`, `">"`, ...), `left` и `right` (поддеревья).
- `LogicalBinOp` – поля `operator` (`"and"` или `"or"`), `left` и `right`.
- `LogicalNot` – поле `operand` (поддерево).

Каждый узел содержит поле `"type"`.

**Пример AST в JSON:**
```json
{
  "type": "LogicalBinOp",
  "operator": "and",
  "left": {
    "type": "Comparison",
    "operator": "<",
    "left": {
      "type": "IndicatorAccess",
      "indicator": "rsi",
      "attributes": ["value"]
    },
    "right": { "type": "Number", "value": 30 }
  },
  "right": {
    "type": "Comparison",
    "operator": ">",
    "left": {
      "type": "IndicatorAccess",
      "indicator": "close",
      "attributes": []
    },
    "right": {
      "type": "IndicatorAccess",
      "indicator": "ott",
      "attributes": ["ott"]
    }
  }
}
```

### 2.4. Интерпретатор
Интерпретатор вычисляет AST, используя **контекст**.

**Интерфейс контекста** (единый для всех языков):
- Метод: `get_value(indicator: str, params: dict, attributes: List[str], offset: int = 0) -> float`
  - `indicator` – имя индикатора.
  - `params` – словарь параметров индикатора (например, `{"period": 14}`). Если не указаны, подставляются значения по умолчанию из манифеста.
  - `attributes` – путь внутри индикатора (например, `["value"]`).
  - `offset` – смещение назад в барах (0 – текущий, 1 – предыдущий и т.д.) для поддержки исторических запросов.
- Метод выбрасывает исключение, если индикатор/атрибут не существуют или параметры невалидны.

**Логика вычисления** (стандартная):
- `Number` → число.
- `IndicatorAccess` → `context.get_value(indicator, params, attributes, offset)`.
- `Comparison` → вычислить левый и правый операнды, применить оператор.
- `LogicalBinOp` → вычислить операнды, применить `and`/`or` (с short-circuit).
- `LogicalNot` → вычислить операнд, вернуть `not`.

Результат – булево значение.

### 2.5. Безопасность
- **Запрещены** вызовы функций, арифметика, доступ к файловой системе и сети, `eval`/`exec`.
- Интерпретатор взаимодействует **только** с контекстом через строгий интерфейс.
- Контекст и провайдеры обязаны проверять разрешённые индикаторы по манифесту.

### 2.6. Обработка ошибок
- **Синтаксические ошибки** – парсер выдаёт сообщение с позицией (строка, столбец) и ожидаемым токеном.
- **Семантические ошибки** (неизвестный индикатор, неверный атрибут, невалидные параметры) – интерпретатор генерирует исключение с понятным описанием.

### 2.7. Протокол подключения индикаторов (Indicator Provider Protocol)

#### 2.7.1. Проблематика
Индикаторы различаются по:
- структуре (простые, составные, с вложенными атрибутами);
- наличию параметров (например, `rsi(14)`, `macd(12,26,9)`);
- языку реализации (Python, C++, Go, внешние микросервисы).

Чтобы DSL оставался чистым и кросс-языковым, вводится **формальный протокол** для получения значений индикаторов.

#### 2.7.2. Контракт провайдера
Каждый источник данных должен реализовать единый интерфейс.

**Запрос (JSON)**:
```json
{
  "indicator": "rsi",
  "parameters": { "period": 14 },
  "attributes": ["value"],
  "bar_offset": 0
}
```

**Ответ (JSON)**:
```json
{
  "status": "ok",
  "value": 45.6,
  "error": null
}
```

При ошибке: `{"status": "error", "error": "описание"}`.

#### 2.7.3. Мета-протокол (Discovery)
Каждый провайдер предоставляет **манифест** со схемой доступных индикаторов, их параметров и атрибутов.

Пример манифеста:
```json
{
  "indicators": {
    "rsi": {
      "parameters": { "period": { "type": "integer", "default": 14, "min": 2, "max": 100 } },
      "attributes": ["value"]
    },
    "macd": {
      "parameters": { "fast": 12, "slow": 26, "signal": 9 },
      "attributes": ["macd", "signal", "hist"]
    },
    "ott": {
      "parameters": { "period": 20, "k": 1.5 },
      "attributes": ["ott", "long"]
    },
    "close": {
      "parameters": {},
      "attributes": []
    }
  }
}
```

Контекст загружает манифест при инициализации. При обращении к индикатору проверяется:
- существование индикатора;
- наличие запрашиваемого атрибута;
- корректность переданных параметров (тип, диапазон).

#### 2.7.4. Адаптеры для разных языков
- **In‑Process адаптер** – провайдер реализован на том же языке, регистрируется как объект, реализующий интерфейс `IndicatorProvider`.
- **Remote адаптер** – провайдер работает как отдельный сервис (HTTP/gRPC), контекст содержит тонкий клиент, который сериализует запросы в протокол.

Кеширование ответов на время одного вычисления исключает дублирующие запросы.

#### 2.7.5. Безопасность протокола
- DSL передаёт только строки и числа.
- Провайдер не имеет доступа к AST или окружению.
- Все параметры валидируются по манифесту до вызова провайдера.

## 3. Нефункциональные требования

### 3.1. Производительность
- Парсинг выражения ≤ 200 символов – ≤ 1 мс.
- Интерпретация AST – ≤ 0.1 мс.
- Запрос к in‑process провайдеру – ≤ 0.5 мс; к remote – ≤ 5 мс (с учётом сети).
- Общее время вычисления (с кешированием AST) ≤ 0.5 мс.

### 3.2. Расширяемость
- Грамматика и AST спроектированы для добавления новых операторов и узлов.
- Паттерн Visitor позволяет легко добавлять новые типы узлов.

### 3.3. Кросс-языковая поддержка
- Спецификация DSL (грамматика, AST, протокол) задокументирована и независима от языка.
- Предоставляется **JSON-сериализация AST** для передачи между компонентами.
- Для каждого языка может быть своя реализация парсера/интерпретатора, но все они соответствуют единой спецификации.
- Рекомендуется референсная реализация на Python (Lark) и обёртки для вызова через gRPC/REST.

### 3.4. Надёжность
- Юнит-тесты покрывают ≥90% парсера и интерпретатора.
- Тесты проверяют сериализацию/десериализацию AST.
- Тесты для провайдеров проверяют корректность манифеста и обработку ошибок.

### 3.5. Переносимость
- Реализация на Python должна работать на Python 3.10+ без привязки к ОС.
- Для других языков – аналогично.

### 3.6. Требования к провайдерам
- Каждый провайдер должен отдавать манифест за ≤ 100 мс (кешируется).
- Провайдер должен быть потокобезопасным.
- Remote-провайдер должен поддерживать параллельные запросы.

## 4. Требования к реализации (референсная версия на Python)

### 4.1. Инструменты
- Парсер – **Lark** (LALR), грамматика в отдельном файле.
- Интерпретатор – чистый Python, без внешних зависимостей.
- Сериализация – стандартный модуль `json`.

### 4.2. Структура модуля
```
dsl/
├── grammar.lark          # грамматика для Lark
├── parser.py             # parse(code: str) -> ASTNode
├── ast.py                # классы узлов AST с to_dict/from_dict
├── interpreter.py        # Interpreter.visit(node, context) -> bool
├── context.py            # контекст (использует провайдеров)
├── serialization.py      # JSON-утилиты
├── evaluate.py           # evaluate_dsl(code: str, context) -> bool
└── providers/
    ├── base.py           # абстрактный класс IndicatorProvider
    ├── manifest.py       # структура манифеста и валидатор
    ├── in_process.py     # адаптер для Python-индикаторов
    └── remote_http.py    # адаптер для HTTP/gRPC-провайдеров
```

### 4.3. API для интеграции
Основная точка входа:
```python
def evaluate_dsl(code: str, context: Context) -> bool:
    ast = parse(code)
    interpreter = Interpreter()
    return interpreter.visit(ast, context)
```
Используется в HTTP-обработчиках и других сервисах.

### 4.4. Пример регистрации провайдера в Python
```python
from dsl.providers import IndicatorProvider

class RSIProvider(IndicatorProvider):
    def get_manifest(self) -> dict:
        return {
            "rsi": {
                "parameters": {"period": {"type": "integer", "default": 14}},
                "attributes": ["value"]
            }
        }
    def resolve(self, indicator: str, params: dict, attributes: list, offset: int) -> float:
        # вычисление RSI с учётом params['period'] и offset
        return calculated_value
```

Контекст регистрирует провайдера и использует его при вызове `get_value`.

## 5. Перспективные требования (вторая очередь)
Заложены в архитектуру, но реализуются позже:

### 5.1. Переменные (let)
Синтаксис: `let <name> = <expr> in <body>`.  
Переменные видимы только в `body`.

### 5.2. Временные зависимости
- Доступ к предыдущим значениям: `indicator[offset]` (смещение в барах).
- Встроенные функции: `rising(expr, n)` и `falling(expr, n)`.

### 5.3. Пользовательские макросы
Определение именованных блоков, раскрываемых на этапе парсинга.

## 6. Этапы разработки и приёмка

### Этап 1. Базовая версия (обязательная)
- Реализация грамматики, парсера, AST, интерпретатора, контекста, протокола провайдеров.
- Реализация как минимум двух провайдеров: простой (`close`) и параметризованный (`rsi`).
- Тестирование на ≥20 примерах (включая синтаксические и семантические ошибки).
- Интеграция с торговым ядром через REST-эндпоинт `/evaluate` (принимает выражение, возвращает результат или ошибку).
- Документация по грамматике, AST, протоколу и интерфейсу провайдера.

**Критерии приёмки:**
- Все корректные выражения вычисляются правильно.
- Ошибки (неизвестный индикатор, неверный атрибут) перехватываются с чёткими сообщениями.
- Время обработки (парсинг + интерпретация + 2 запроса к провайдерам) ≤ 2 мс.
- Манифест успешно загружается и используется для валидации.

### Этап 2. Расширенная версия (по желанию)
- Реализация `let`, исторических значений, `rising`/`falling`.
- Обновление тестов и документации.

## 7. Дополнительные рекомендации по кросс-языковости
- Для упрощения интеграции с языками, не имеющими реализации DSL, можно развернуть **микросервис DSL**, который принимает выражение и контекст (словарь значений индикаторов) и возвращает результат.
- Для высоконагруженных систем – библиотека-клиент на каждом языке с кешированием AST и вызовом сервиса по gRPC.

## 1. Контекст

Тезис проекта — «решения принимает только детерминированный код» — неполный без Risk
Engine: сейчас риск-параметры (TP/SL, ATR-мультипликаторы) разрознены
(`ai/src/features.py`, конфиги), а лимитов позиций/просадки нет вовсе.
TZ-11 закрывает пробел **без хардкода**: правила и лимиты — это **данные** (конфиг),
движок — их интерпретатор. Код содержит только инварианты безопасности.

## 2. Место в системе

```
DSL-сигналы (+P(win)) → Risk Engine (TZ-11) → приказы (объём, SL/TP) → исполнение (TZ-04 движок)
```

Вне контура: LLM не имеет ни импорта, ни транспортного доступа (TZ-09 не содержит
команды изменения лимитов — проверяется тестом на схему очередей).

## 3. Принцип: конфиг — данные, движок — интерпретатор

| Слой | Что это | Гибкость |
|------|---------|----------|
| **Движок** (`risk/engine.py`) | гоняет сигнал через упорядоченные правила, собирает `Decision`; кода правил НЕ содержит | жёсткий код |
| **Реестр правил** (`risk/rules/`) | `name` → класс-реализация правила | расширяется кодом, включается/отключается данными |
| **Конфиг** (`configs/risk.yaml`) | набор и порядок правил (`engine.rules`) + параметры (`params`) | только данные, без правки кода |

Неизменное правило TZ-11: **любое изменение лимитов/порогов/состава правил достижимо
правкой конфига, без изменения исходников.** Хардкод порогов (магические числа)
запрещён — всё, что влияет на решение, читается из конфига при старте.

## 3.1. Схема конфига (типизированная)

`configs/risk.yaml` → frozen-dataclass-конфиг (как `ai/src/config.py`) со строгой
валидацией: `Extra.forbid` (неизвестный ключ = ошибка), проверка типов и допустимых
значений при `validate_config()`. Пример:

```yaml
engine:
  rules:                     # порядок применения
    - name: require_stop_loss
      active: true
      params:
        tp:  { min_mult: 1.0 }             # пороги как данные, не код
        sl:  { min_mult: 0.0, use_atr: true, atr_lookback: 14 }
    - name: position_limit
      active: true
      params: { max_capital_pct: 0.1, max_units: 10000 }
    - name: max_positions
      active: true
      params: { max_open: 5 }
    - name: daily_loss_limit
      active: true
      params: { max_daily_loss_pct: 0.02 }   # лимит на день
    - name: drawdown_stop
      active: true
      params: { max_drawdown_pct: 0.2, pause_bars: 60 }

portfolio:                 # per-инструмент оверлайды (перекрывают engine-level)
  max_capital_pct: 0.1
  instruments:
    "TQBR.FIGI": { max_capital_pct: 0.05, max_units: 5000 }
```

### 3.2. Иерархия переопределения (не хардкод, не «дроп-конфиг»)

```
defaults  configs/risk.yaml        → инспектируемые дефолты
                              ↓
user      --config <file>.yaml     → мерж (глубокий), неизвестные ключи → ошибка
                              ↓
env       RISK_*                   → строгие оверрайды (только объявленные в схеме)
```

- `validate_config()` запускается на каждом слое загрузки;
- запись любого значения вне объявленной схемы (тип/неймспейс/перечисление) — ошибка,
  а не тихое игнорирование.

## 3.3. Формат правила = «contract»

Каждое правило в `engine.rules`:
- `name` → класс из реестра `risk/rules/` (single source логики);
- `params` → только данные (нет кода в конфиге);
- `active: true|false` → включается/выключается без правки кода;
- `severity: enforce|warn` → **в v1 допустим только `enforce`** (полу-режим `warn`
  размывал бы тезис детерминизма; запрет до прохождения Baseline-gate TZ-04 п.4.6.1).

## 4. Требования

1. Пакет `risk/` — workspace-член **`dte-risk`** (deps: numpy, pyyaml); **решение
   зафиксировано**: отдельный пакет, не секция в strategies (живой и критичный).
2. Конфиг по п.3.1–3.3 без хардкода; `validate_config()` при загрузке.
3. API: `check(signal, portfolio, cfg) -> Decision{approve, reason, size}` — чистая
   функция, без IO, без времени внутри (время/дата — параметр).
4. Реестр правил (v1): `require_stop_loss`, `position_limit`, `max_positions`,
   `daily_loss_limit`, `drawdown_stop`; каждое — по «contract» п.3.3.
5. Интеграция: бэктест TZ-04 вызывает `check()` на каждом сигнале; live-контур TZ-10 —
   тот же `check()` (принцип №2 TZ-00: один движок на три потребителя).

## 5. Что жестко НЕ конфигурируется (инварианты безопасности = код + тесты)

Эти гарантии реализованы в коде и тестах, не зависят от конфига и не могут быть
ослаблены правкой YAML:
- **нет approve без прохождения всех активных правил** — ни один путь не выдаёт приказ;
- **нет команды «изменить лимиты» в протоколе TZ-09** — тест на схему очередей;
- **`size=0` при пустом/недостаточном капитале**;
- **реектор и движение порогов каузальны** (ATR из данных ≤ t, TZ-04 п.4.1.5).

## 6. Критерии приёмки

- **Config-driven**: два разных конфига при одном коде дают разное поведение
  (смена порогов/состава правил без правки исходников) — e2e-тест.
- **Валидация**: неизвестный ключ / неверный тип / запрещённый `severity: warn` →
  ошибка во время `validate_config()`, не тихий ignore.
- **Edge-кейсы**: SL/TP ≤ порога → reject; превышение дневного убытка →
  reject до конца дня; MaxDD-стоп → пауза; `size=0` при пустом капитале.
- **Инварианты**: нет approve без всех активных правил; TZ-09-протокол не содержит
  «изменить лимиты».
- `uv run --package dte-risk pytest` зелёный.

## 7. Перекрёстные связи

- TZ-04: движок исполнения принимает `Decision`; отчёт хранит reject (имя правила,
  параметры на момент отказа, счётчик).
- TZ-09: контракт очередей не содержит команды изменения `engine.rules/params`
  (тест на схему).
- TZ-14: риск-конфиг рендерится/валидируется через те же механики типизированного
  конфига, что `ai/src/config.py`.
